# /verify — 代码变更后完整流程

## 何时执行

任何 `.ts` / `.js` / `.json` 文件被修改后，**按以下流程逐项走完**：

```
修改代码
  ↓
① 五道核验（编译·功能·牵连·服务·监控）
  ↓  有一道不过 → 回退→诊断→修→重验
  ↓  五道全过 ↓
② 提交（本地 git commit）
  ↓
③ 输出改善报告（改了啥·为什么·核验证据·注意事项）
  ↓
④ 问用户："是否上传同步？"
  ↓
⑤ 用户确认后才 git push
```

**铁律**：
- 永远不自动推送。每次推送前必须等用户确认。
- 改善报告必须有核验证据（命令输出），不是"应该没问题"。
- 如果用户说"继续"但没有明确说"上传/推送/同步"，不推送。

---

## ① 五道核验

### 第一道：编译检查

```bash
npx tsc --noEmit 2>&1 | grep -c "error TS"
```

✅ 通过标准：错误数 ≤ 改动前基线。

### 第二道：功能验证

**改了哪个功能 → 用真实输入驱动那个功能 → 观察输出。**

| 改了什么 | 怎么验证 |
|---------|---------|
| 存储层 | 写入后 SELECT 确认数据正确 |
| 检索层 | 发送相关消息，确认检索结果符合预期 |
| 注入层 | 检查对应日志输出或 LLM 回复行为 |
| 前端/路由 | curl 对应端点，确认响应正确 |
| 数学/评分 | 构造已知输入，验证计算输出 |

❌ **不接受**："逻辑上没问题"、"代码看起来正确"、"之前测过这条链路"。

### 第三道：牵连模块核查

改了 A → 列出所有依赖 A 的 B、C、D → 逐一核查。

```bash
grep -rn "from '.*<被改文件名>'" src/ --include="*.ts"
grep -rn "import.*<被改符号>" src/ --include="*.ts"
```

### 第四道：服务状态

```bash
curl -s http://localhost:3000/api/health | python3 -c "import sys,json;d=json.load(sys.stdin);print(d['status'],d['alignment']['status'])"
```

✅ 通过标准：`ok healthy`。

### 第五道：监控与前端

```bash
# 监控看板
curl -s http://localhost:3000/_hooks/monitor | python3 -c "import sys,json;d=json.load(sys.stdin);cs=d['cards'];print(f'cards={len(cs)} green={sum(1 for c in cs if c[\"status\"]==\"green\")}')"
# 关键前端页面
curl -s http://localhost:3000/monitor | grep -c "<title>"
```

## ② 提交

```bash
git add <改动文件>
git commit -m "<描述>"
```

**提交到本地**——不推远程。

---

## ③ 改善报告

```
## 📋 改善报告

### 改了啥
[简述]

### 为什么
[根因]

### ✅ 核验

| 道 | 核查项 | 结果 | 证据 |
|:--:|--------|:--:|------|
| 1 | 编译 | ✅/❌ | N 错误，零/X 新增 |
| 2 | 功能 | ✅/❌ | [具体输出] |
| 3 | 牵连 | ✅/❌ | [列出检查过的模块] |
| 4 | 服务 | ✅/❌ | health ok |
| 5 | 监控 | ✅/❌ | cards正常 |
```

---

## ④ 上传确认

改善报告输出后，问用户：

> 是否上传同步？

用户的回答才决定是否执行 `git push`。

**用户说"继续"但没有明确说"上传/推送/同步" → 不推送。**

---

## 发现问题的处理

核验不过：
1. **立即回退** → `git checkout <commit> -- <file>`
2. **诊断根因** → 为什么没过
3. **修复** → 全过才能宣告完成
