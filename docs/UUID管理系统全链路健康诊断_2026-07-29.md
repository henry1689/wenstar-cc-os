## 二、UUID 生成链路

### 2.1 格式：TXS-XXXXXXXXX（全局自增序列）

`FamilyGraph._generateUUID()` — 纯序号计数器，`_category` 参数接收但**未注入到 ID 中**。所有新节点 UUID 均为 `TXS-{seq}` 格式。

V3.2 迁移期有少量 `A-00001`、`G-00002` 格式（`_formatUUID(category, seq)` 双参数调用），与运行时不一致，但迁移后不再产生。

### 2.2 分类推断逻辑（三层优先级）

1. 硬编码名："玉瑶"→S, "我"→U
2. edges 表关系：有 family edge → A；social edge → B/C/D/E/F
3. `relation_to_user` 文本关键词匹配："情人"→X, "同事"→B, "同学"→D... default→G

### 2.3 "我"节点特殊处理

`U-00001` 固定 UUID，`SELF-00001` 固定 node ID，不经过 normal pipeline。

## 三、UUID 录入链路

### 3.1 写入路径

```
用户消息 "找熊梓铭聊聊"
  │
  ▼
persistence-stage.ts: EntityOwnershipResolver.resolveOwnership()
  ├── ① entity_genes 匹配: 取第一个 type='person' → FG.getUUIDByName("熊梓铭")
  ├── ② 自称检测: 6种中文自称正则 (仅助理回复)
  ├── ③ 显式指名: 遍历 FG.getAllPersonNames() 做 substring 匹配
  └── ④ 兜底: null
  │
  ▼
belongUUID → conversationDB.insertConversation() + sqlite.writeMemory()
```

### 3.2 新实体首次提及的缺口

```
1. 用户首次提及 "熊梓铭" → FG 中尚无此节点
2. EntityOwnershipResolver 四级解析全部失败 → belongUUID = null
3. conversation + memory 写入时 belong_entity_uuid = NULL
4. 同一轮对话中 FG.addNode("熊梓铭") 创建节点并生成 TXS-ID
5. 但步骤3的记录不会即时回填 → UNTIL NEXT RESTART
```

**无进程中即时回填机制**。新实体首次对话的记录在重启前始终为 NULL。

### 3.3 black_diamond 表严重缺陷

`black_diamond` 表的 DDL（schema.sql）中**没有** `belong_entity_uuid` 列。该列通过隐式 ALTER 添加，但存在两个可能：

- 若数据库创建后该 ALTER 成功 → 列存在但无索引
- 若数据库创建后该 ALTER 失败（被 try/catch 吞掉） → 列不存在

当前数据中 black_diamond 63% 标注率说明列大概率存在，但**写入路径中没有显式赋值**——所有手动写入的 19 条 XZM 黑钻是在 SQL 脚本中直接赋值的，非 pipeline 行为。

## 五、UUID 检索链路 — 最严重区域 🔴

### 5.1 四层存储的 UUID 过滤状态

| 存储层 | 搜索路径 | UUID 过滤存在？ | UUID 过滤在工作？ |
|:---|:---|:---|:---|
| conversations | UnifiedSearchEngine V11 | ✅ | ✅ |
| conversations | 情感相似度搜索 | N/A | N/A（不查此表） |
| memories | UnifiedSearchEngine V11 | ✅ | ✅ |
| memories | **情感相似度搜索（主力路径）** | ✅ API 支持 | 🔴 **从未传递** |
| memories | 砂金库高钙化检索 | ✅ | ✅ |
| memories | 金库检索 | ❌ | ❌ 无UUID过滤 |
| black_diamond | UnifiedSearchEngine V11 | ✅ | ✅（但 search_index 中 black_diamond=0） |
| knowledge_base | UnifiedSearchEngine V11 | ✅ | ✅ |
| knowledge_base | **KB 直搜** | ❌ | 🔴 **无UUID过滤** |
| knowledge_base | **KnowledgeContextBuilder** | ✅ API 支持 | 🔴 **从未传递** |

### 5.2 关键症结：retrieval-stage 的情感相似度搜索从未传 entityUuids

```typescript
// retrieval-stage.ts:127 — 主情感检索路径
// entityUuids 已在该文件前段收集到了 _activeUuids
// 但下传给 findByEmotionalSimilarity 时，只传了 entities（名字），没传 entityUuids（UUID）
ctx.storage.findByEmotionalSimilarity({
  current_perception: p, similarity_mode: mode,
  entities: uniqueExpanded, limit: _memLimit + 3,
  // ⚠️ entityUuids: _activeUuids ← 从未传递
});
```

`SQLiteAdapter.findByEmotionalSimilarity()` 的 `RetrievalQuery` 类型**声明了** `entityUuids?: string[]` 字段，SQL 层也支持此过滤。但调用方从未传递。

### 5.3 KnowledgeEngine 的 UUID 参数从未被使用

```typescript
// knowledgeEngine.weightedSearch() 声明了 belongEntityUuid 参数
// 但唯一的调用方 KnowledgeContextBuilder.buildPreM4Context() 从未传递
const hits = ctx.knowledgeBase.weightedSearch(
  keyword, sceneTags, perception, limit
  // ⚠️ 缺少: , belongEntityUuid
);
```

### 5.4 search_index 中 black_diamond = 0 条

`rebuildAllIndexes()` 方法的第四步（黑钻索引构建）**从未被实际调用**——因为服务端启动时只检测 `isIndexEmpty()`，而 search_index 已有 697,073 条其他表数据，所以不会被判定为"需要重建"。

这意味着你手动写入的 **19 条 XZM 黑钻条目无法被 n-gram 搜索命中** — 即使 U11 搜索引擎正确传递了 UUID 过滤也无济于事。

### 5.5 知识库完整档案为空

`kn_xzm_research_complete` 的 `content` 为**空字符串** — 写入脚本的 CJS/ESM 兼容性问题导致 exec 写入了空值。16,373 字的完整叙事档案实际上**从未存入数据库**。所以 KnowledgeEngine 的 BM25 索引也搜不到它。

## 六、UUID → LLM 上下文 → 回复 链路

### 6.1 MemoryInjector 无实体感知

`MemoryInjector.injectMemories()` 将所有来源（情感记忆/UnifiedSearch/KB直搜/砂金/金库）合并为单一 `memoryText` 字符串，不做实体标记。来自不同实体的记忆被混合后作为 `【情感背景·过往记忆】` 注入 LLM。

### 6.2 会晤模式的全部阻断

当 `_meetingEntityName` 被设置时，`retrieval-stage.ts:43` 直接返回空结果。**会晤实体拿不到任何用户记忆** — 这是一个设计选择（防止泄漏）但在 UUID 过滤健全的情况下是不必要的极端。

### 6.3 用户问"熊梓铭你还记得纪实研究吗"时的实际路径

```
① retrieval-stage 黑钻 LIKE "纪实研究" → 0 hits（summary不含这6字连串）
② retrieval-stage 情感相似度 → 按情感向量搜，不关心文本内容 → 返回随机记忆
③ UnifiedSearchEngine n-gram → 纪实/实研/研究/究小/小说 → 但 black_diamond 索引=0
④ KnowledgeEngine.search("纪实研究", 3) → 1 hit（地标，不是完整档案）
⑤ kn_xzm_research_complete 完整档案为空 → 无法命中
⑥ 19条手动写入黑钻 → 无法命中（无索引 + 无 LIKE 匹配）
⑦ 最终注入 LLM 的记忆片段: 不包含任何纪实研究内容
⑧ LLM 回复: "我不太记得了..." 或编造
```

## 七、总结：问题分级

### 🔴 P0 — 搜索层不可用

| # | 问题 | 影响 |
|:--:|:---|:---|
| 1 | retrieval-stage 情感搜索未传 entityUuids | 主力检索路径（40-50%流量）无实体隔离 |
| 2 | black_diamond 无 search_index | 全部黑钻条目无法被 n-gram 搜索命中 |
| 3 | kn_xzm_research_complete 为空 | 知识库完整档案丢失，需重写 |

### 🟡 P1 — 数据一致性

| # | 问题 | 影响 |
|:--:|:---|:---|
| 4 | 10个垃圾实体在 FG 中 | 污染 FG 节点表 |
| 5 | entities 与 FG 不同步（12缺/2多余） | 同名多UUID风险 |
| 6 | 新实体首次对话 UUID=NULL，需重启回填 | 首次对话记忆无法按实体召回 |
| 7 | black_diamond DDL 缺少 belong_entity_uuid | 列创建可能静默失败 |

### 🟢 P2 — 优化项

| # | 问题 | 影响 |
|:--:|:---|:---|
| 8 | KnowledgeContextBuilder 未传 belongEntityUuid | 知识库检索无实体过滤 |
| 9 | 金库检索无 UUID 过滤 | vault_log 搜索结果跨实体 |
| 10 | MemoryInjector 无实体感知 | 不同实体记忆混合注入 LLM |
| 11 | 会晤模式全阻断检索 | 会晤实体拿不到任何记忆 |
